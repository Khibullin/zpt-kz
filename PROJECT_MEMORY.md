## 1. Назначение и бизнес

**ZPT.KZ** — платформа автозапчастей и услуг автобизнеса в Казахстане:
- розничная и оптовая витрина;
- заявка покупателя на подбор запчастей и уведомление подходящих продавцов;
- кабинет продавца, товары и условия оптовых продаж;
- подбор СТО и детейлинга;
- внутренние инструменты склада, продаж Kaspi, маркетинга и управления.

Собственный ассортимент AG Parts развивается внутри платформы. Продавцы сайта, продавцы рассылки заявок и исполнители услуг имеют разные модели данных; их нельзя автоматически считать одной сущностью.

Названия «CPT», «CPTKZ» в текущем поручении трактуются как обозначение этого проекта. Фактическое название найденного репозитория — `Khibullin/zpt-kz`. Отдельный репозиторий CPTKZ не подтверждён.

## 5. Основные процессы

### Заявки на запчасти

Покупатель создаёт заявку → подбираются продавцы → формируется очередь `RequestDispatch` → уведомления отправляются волнами → покупатель открывает защищённую заявку и историю.

Основные места: `core/views.py`, `core/buyer_portal.py`, `core/management/commands/dispatch_request_waves.py`.

Buyer receipt и seller dispatch — разные процессы. Не создавать второй sender, signal или повторную отправку для уже существующего события без проверки идемпотентности.

Ссылка продавцу `/sr/<token>/` реализована. По ранее подтверждённому контракту: неизвестный token → 404, просроченный → 410; TTL по умолчанию два часа, noindex/nofollow и no-store. Текущие детали смотреть в `core/seller_request_link_views.py` и `SellerRequestAccess`.

### Каталог, корзина и заказ

Правило: один продавец — одна корзина — один заказ. В текущем коде есть canonical seller resolver и связь Order с SellerProfile; прежнее сопоставление только по телефону не считать полной архитектурой.

Поддерживаются розница/опт, снимки данных и условий продавца, способы доставки: самовывоз, курьер по городу, доставка по Казахстану. Наличие вариантов в форме не означает интеграцию перевозчика.

Статусы заказа: `new → confirmed → awaiting_payment → paid`, либо `cancelled`. Ручной checkout и email администратору остаются частью реализации. Защищённая страница результата использует UUID.

### Оплата

Robokassa Kazakhstan: первый этап — тестовые платежи, подписи и обработка callback. `ROBOKASSA_LIVE_ENABLED = False` задаётся непосредственно в settings; переменная окружения не снимает блокировку.

Не считать redirect success доказательством поступления денег; сверять подтверждение в callback и тестах payments. Квитанции/фискализация и расчёты с внешними продавцами не подтверждены как реализованная боевая схема.

### Склад и Kaspi

Физический остаток склада, доступность витрины, факт выгрузки Kaspi и рекомендации цены — разные уровни данных.

- **PP1:** резервный/статичный склад для планирования пополнения.
- **PP2:** динамический продающий склад Fulfillment/Rapido.
- Доступность Kaspi рассчитывать из PP2; **PP1 + PP2 не суммировать**.
- Общий физический запас нельзя целиком продублировать на каждую Kaspi-карточку одного товара.
- Остатки изменять через `catalog/stock_service.py` с журналом `StockMovement`, не прямой записью quantity.
- `Product.stock_qty` и `ProductWarehouseStock.quantity` не являются взаимозаменяемыми.
- Импорт фактов Kaspi не должен подменять физический остаток PP2.
- Импорты inventory, sales, listing facts и reconciliation имеют отдельные команды. Перед записью изучить `--help`, выполнить preview/dry-run и проверить сопоставление.
- Repricer и stock preview не считать автоматическим изменением цены/остатка в кабинете Kaspi.

### Привлечение и контент

В коде есть discovery/enrichment SellerLead, классификация, источники, доказательства и дубликаты. Найденный контакт не равен подтверждённому продавцу; согласие на сообщения учитывать отдельно.

InstagramPublication содержит размещения и очередь попыток; публикация управляется флагами. SEO-материалы используют draft/review/published, кандидаты и связанные товары. Подготовка AI-черновика не должна автоматически публиковать материал.

- Тексты/картинки не должны обещать неподтверждённую совместимость, наличие или способ оплаты.

### Render

`render.yaml`: build — `bash build.sh`; start — `gunicorn backend.wsgi:application --bind 0.0.0.0:$PORT`.

`build.sh` выполняет:
1. установку зависимостей;
2. `migrate --noinput`;
3. `import_car_catalog_kz`;
4. `collectstatic --clear --noinput`.

По истории проекта push в main запускает автодеплой; текущие настройки Render не проверялись.

Cron рассылки управляется вручную. Комментарии render.yaml описывают `dispatch_request_waves` каждую минуту и отдельный `process_marketing_live_sends`. Наличие активных заданий проверить в Render. Не создавать дублирующие cron из Blueprint.

Persistent Disk для медиа предлагается подключать вручную с `MEDIA_ROOT=/var/data`. Фактическое подключение диска не подтверждено. Не менять путь и не переносить медиа без проверки существующего хранилища.

## 11. Contribution Guide

1. Сначала прочитать PROJECT_MEMORY.md, затем код затрагиваемого процесса и применимые инструкции репозитория.
2. Начинать со свежего main в отдельной ветке/worktree. Проверять git status, чтобы не включить чужую незавершённую работу.
3. Рекомендуемые ветки: `feature/<topic>`, `fix/<topic>`, `docs/<topic>`. Это соглашение документа, не подтверждённое обязательное правило CI.
4. Рекомендуемые коммиты: `feat: ...`, `fix: ...`, `docs: ...`, `test: ...`. Описывать конкретный результат.
5. Менять только нужную область. Для бизнеса использовать существующие сервисы, seller resolver и stock service.
6. Не коммитить .env, токены, пароли, БД, локальные отчёты покупателей/продавцов и случайные медиа.
7. Проверять diff; для функциональных изменений выполнять подходящие тесты и migration checks.
8. Не использовать force push в main, не переписывать общую историю и не менять git config без необходимости.
9. Commit/push выполнять в пределах поручения пользователя. Просьба положить документ в репозиторий разрешает запись документа; не разрешает включить платежи/LIVE-рассылки.
10. Не менять одобренные Meta-шаблоны и buyer receipt без отдельного основания; согласовать изменение payload с контрактом Meta.
11. При изменении CSS/JS учитывать кэш WhiteNoise и версию подключения в шаблоне.
12. Личные страницы — токены, noindex; пользовательский ввод экранировать. Проверять права внутренних интерфейсов.
13. После завершённой задачи обновить соответствующий раздел этой памяти, дату и исходный SHA; состояние «развёрнуто/проверено» указывать только с подтверждением.

## 12. Передача работы следующему разработчику

Перед изменениями выяснить:
- совпадает ли main с production;
- применены ли новые миграции;
- какой процесс сейчас реально включён и какими флагами;
- какие данные являются физическим остатком, фактом Kaspi и лишь preview;
- относится ли задача к каталогу, заявкам, заказам, маркетингу или другому приложению;
- не существует ли уже нужная основа в моделях, сервисах и тестах.

Не использовать историю как замену проверки кода. Незавершённую задачу записывать с конкретным оставшимся шагом. Изменения данных production фиксировать отдельно от изменений кода.
