# Утверждённый маршрут заявок, 23.10.2026

Владелец согласовал экраны 1–41 и поручил остальные необходимые состояния выполнить самостоятельно. Это развитие действующих Request / Seller / Match / RequestDispatch / SellerRequestAccess, а не новый каталог заявок.

## Переходы

| Экраны | Реализация |
|---|---|
| 1–5 | `/connect/buyer/<id>/<uuid>/step/accepted`, `sellers`, `edit`, `result`; карточка продавца внутри того же приватного контекста |
| 6–8 | Существующий `connection_detail`, отдельные `contact/` и `result/`; предложение необязательно и свёрнуто |
| 9–11 | Общий поток с фильтрами/моими откликами, карточка и рейтинг, редактирование существующего Seller |
| 12–17 | Подключение, поиск существующего телефона, короткая форма нового магазина, запрос/проверка доступа, одноразовый вход через проверенный контакт |
| 18–19 | Истёкшая ссылка и закрытая заявка; без выдачи контактов |
| 20–24 | Покупка без обязательного продавца, добровольная атрибуция, отзыв, завершение, повторный поиск/закрытие |
| 25–32 | Контроль/история в существующей админке, подготовка/состояние Telegram, ручная сверка публикации, проверка продавца, список заявок |
| 33–37 | Раздельные согласия каналов, безопасная привязка бота, подтверждение в боте, явное персональное уведомление |
| 38–40 | WhatsApp вручную, вопрос о результате в одном согласованном канале, ручная отправка через существующий RequestDispatch |
| 41 | Ручная приостановка/восстановление уведомлений с основанием и журналом, без удаления Seller |

Точки входа для сотрудников: `/connect/staff/requests/`, ссылка «Контроль и история заявки» в Request admin, «Активность продавца» в Seller admin, список SellerAccessClaim. Доступы сотрудников проверяются и при прямом POST.

## Личность и согласия

Поиск телефона показывает только название/город и не авторизует. Одобрение заявки НЕ авторизует браузер заявителя: сотрудник передаёт короткоживущую одноразовую ссылку через проверенный контакт магазина. Только её погашение создаёт/подключает пользователя с непригодным для парольного входа паролем и открывает сессию. Администратор обязан записать основание проверки. Подтверждение продавца — не гарантия наличия или качества товара.

Действующий вход пропускает подключение. Для уже привязанного Telegram есть вход через одноразовый запрос, подтверждение в боте и завершение только в исходном браузере. Случайный username/номер не используется как доказательство. Старый парольный вход сохранён как дополнительный путь существующим пользователям.

Webhook `/connect/telegram/webhook/` требует отдельный `TELEGRAM_CONNECTION_WEBHOOK_SECRET` в заголовке Telegram. При отсутствии секрета endpoint закрыт. Бот принимает привязки и подтверждения только в личном чате с совпадением chat_id/from.id, ограниченным сроком и одноразовым токеном. Секрет бота читается существующим сервисом только из окружения, не выводится. GET не отправляет сообщений. Настройка webhook выполняется отдельно при запуске; код сам её не меняет.

Согласие Telegram/WhatsApp хранится отдельно по каналам и журналируется. Привязка не включает согласие. Отзыв согласия и отключение Telegram останавливают новые уведомления. Уведомления не определяют доступ к общему потоку. Для анонимного просмотра показываются только вручную проверенные summaries с публичным согласием. Подтверждённые продавцы видят общий обезличенный поток независимо от полноты карточки.

## Результаты

Клик → подтверждение общения → возможность поставки → подтверждение покупателя — разные события. Покупатель может подтвердить покупку без Match и без продавца. В таком случае ни одному продавцу покупка не начисляется. Выбор продавца ограничен участниками этой заявки. Изменение результата сохраняет историю, снимает устаревшую атрибуцию и отзыв. Повторный поиск не создаёт Request-дубль.

Изменение описания покупателем снимает `seller_feed_enabled` и очищает публичный summary до ручной проверки; сырое описание/фото не попадает в канал. Фотография сохраняется в существующий RequestPhoto. Уже опубликованный текст нельзя незаметно заменить новым необработанным описанием.

Отзыв добровольный. Публичный показ — только при отдельном согласии и модерации; контакты/VIN/ссылки блокируются при одобрении. Имя покупателя не выводится. Рейтинг сохраняет приоритет применимости и сопоставимых условий; полнота карточки, подтверждённые покупки и отзывы — дополнительные признаки, без вымышленных баллов и санкций за неизвестную доставку.

## Отправки и публикации

Автопубликация в публичном канале и Meta API не включаются. Публикация — отдельный POST сотрудника над проверенным черновиком с согласием покупателя. `sending/unknown/published` нельзя отправить повторно. Ручная привязка разрешена после проверки канала/принадлежности сообщения сотрудником, журналируется и не вызывает sendMessage. №515 остаётся существующим сообщением /5, никаких живых изменений в этой ветке не выполнялось.

WhatsApp ручной экран использует существующие `prepare_manual_dispatch` / `confirm_manual_dispatch_sent`, сохраняет их фильтры, проверки и историю RequestDispatch. Открытие чата не отмечает отправку; отметка сотрудника не доказывает доставку или контакт. Для №515 не расширяется ранее разрешённая пара получателей.

Персональные уведомления Telegram реализованы как явные команды, никакого запуска из migration/save/GET:

```
python manage.py send_seller_telegram_request --request ID --seller ID
python manage.py notify_telegram_request_subscribers --limit 50
python manage.py send_buyer_result_question --request ID
```

По умолчанию только план. Реальная отправка требует `--apply --actor STAFF_ID` и соответствующего права. Пакетная команда выбирает только новые заявки ПОСЛЕ последнего явного согласия продавца, не пересылает историю. После неопределённой отправки повтор блокируется. Автозапуск/расписание не устанавливаются этой веткой.

Для Telegram покупателя предусмотрено отдельное подключение с приватной страницы заявки и подтверждением в боте. Произвольный buyer_telegram username не используется для отправки ботом. Экран администратора «Уточнить результат» предлагает подключённый Telegram или ручной WhatsApp; вопрос отправляется одним каналом, повтор блокируется. Отправка вопроса не меняет результат заявки.

## Проверки и выпуск

Локальные проверки только на временной БД, Telegram API замокан. В миграциях только добавление схемы, без отправок и массовой правки реальных продавцов. Новые endpoint закрыты тем же `TWO_WAY_REQUESTS_ENABLED`. Для выкладки нужны миграции, HTTPS webhook с секретом, проверка бота на синтетических данных и сохранение `MANUAL_REQUEST_PROCESSING=true`. Ветка сама не меняет Render, Meta или production.
