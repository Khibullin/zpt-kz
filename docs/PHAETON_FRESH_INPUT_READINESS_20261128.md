# Готовность нового цикла закупочного поиска Фаэтона

Задание владельца — начать заново со свежего прайса, выбрать категории, подготовить INPUT и самостоятельно запустить его в Apify. Остановленная сессия 6671 не возобновляется, старые выгрузки не переобрабатываются. Проверка реализации выполняется на изолированных тестовых данных.

## INPUT

Новые сохранённые запросы имеют версию `name_article_v5`. Поиск: название детали без бренда и лишнего повторного артикула плюс полный исходный артикул; второй запрос — артикул отдельно. Написания ML9108R, ML 9108R, ML-9108R в названии не создают повтор номера в строке поиска. Бренд результата всё равно проверяется отдельно, буквы/цифры и L/R не теряются.

Новые INPUT используют `sortOrder: price-asc`, до 20 карточек на запрос и город, `includeOffers: true`, `maxOffersPerProduct: 0`, без отзывов. Добавляются сохранённые валидные ссылки выбранных SKU. Используются выбранные города и прежние настройки прокси KZ. Цена по ограниченной выборке не подтверждает минимум всего Казахстана.

Параметры проверены по первичному источнику: https://apify.com/firsthand/kaspi-api/input-schema . Версии v1–v4 воспроизводят прежние запросы и сортировку; для нового INPUT нужно сохранить новый запрос. Общее число поисковых строк показывается до скачивания; размеры файлов и лимит расходов остаются под контролем владельца. Подготовка JSON сама по себе не запускает Apify.

## Привязка к свежему прайсу

Обнаруженный разрыв: отбор читал staged PriceUpdate, а загрузка цен считала по Offer. Для нового запроса это могло использовать старую закупочную цену и старый остаток. Теперь сессия результатов сохраняет связь с конкретным запросом, ID и SHA исходного прайса. Проверка хеша выполняется до обработки. Наличие, закупочная цена, базовое название/категория и дата для расчёта берутся из снимка запроса. Существующий Offer остаётся неизменным; отсутствующий выбранный SKU создаётся только после точного совпадения и получения реального предложения продавца.

Внутреннее имя источника аудита — request_ID.json. Все полученные файлы одного нового запроса агрегируются в общий минимум; исходные имена файлов остаются в сессиях и доказательстве выбранной цены. Поэтому новый файл с тем же именем не заимствует прежний минимум или прежние финансовые снимки. Возобновление той же незавершённой загрузки допускается только в её запросе; уже использованный JSON другого запроса не выдаётся за новый результат. Сохраняются исходные значения JSON. Полный файл выбирается один раз, внутренние партии по 500 продолжают общий минимум по файлу.

Выбранный запрос в блоке 2 передаётся при загрузке результатов; сохраняется и резервная привязка в пользовательской сессии после подготовки INPUT. Поставщик запроса проверяется. Новый прайс или сохранение нового запроса снимает текущую экранную привязку к прежней загрузке, не удаляя историю и не продолжая остановленный процесс. Устаревшая вкладка обработки с другим session_id не может начать обрабатывать новую загрузку.

## Результат

Прибыль и доходность считаются с новыми закупочными данными и прежними настройками комиссии/расходов. Упаковка учитывается один раз. Финансовые пороги не меняются. Публикация подходящих позиций в реестре идемпотентна: уже имеющиеся товары получают доступ к новому расчёту без создания дубля и без перезаписи исторического PermanentBuyingItem. Ссылка «Посмотреть товары» доступна после завершения и открывает только новый источник, включая пустой результат. Для новых снимков карточка сравнения показывает ту же закупочную цену и дату прайса, что участвовали в расчёте.

Тестовый пример: старый каталог — закупка 3000 и остаток 0; выбранный новый прайс — закупка 6000 и остаток 5. При минимальной Kaspi-цене 10000, комиссии 12,5% и расходах 250 получаются прибыль 2500 и доходность 41,6667%, поэтому товар не проходит порог 50%. Старая цена 3000 не создаёт ложную выгодность. Старый аудит на 2000 сохраняется отдельно и не подмешивается в новую выгрузку. Такой же SKU Omega и SKU вне запроса не изменяются.

## Проверка владельцем

После публикации загрузить свежий прайс в блоке 1, выбрать небольшую категорию для пробы и сохранить новый запрос. В блоке 2 сформировать новый JSON и запустить его вручную в Apify. Результат загрузить целиком при выбранном том же запросе, завершить обработку и применить расчёт. Сверить несколько выбранных карточек и цены продавцов с Kaspi перед расширением отбора. Платный запуск и проверка актуальных цен по новому прайсу этой доработкой не выполняются.
