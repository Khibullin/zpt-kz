# Apify 21.11.2026 — ночной проход 9: прямая сверка первичных офферов и защита от аналога

Дата: 22.11.2026. Только review-ветка, без изменения production.

## Новая независимая проверка оригинального Apify JSON

Оригинальный файл `dataset_kaspi-api_2026-11-21_14-00-09-125.json` найден в файловой библиотеке. Его сырые байты по-прежнему не разрешено материализовать, но удалось безопасно прочитать **сами исходные текстовые объекты всех 27 карточек Kaspi, относящихся к 18 предварительным SKU** (включая дополнительные карточки одинакового артикула), а не только сокращённый staging-реестр. Для каждой проверены следующие независимые условия:

- ровно один объект с ожидаемым `id`, подлинный заголовок и ссылка из исходного файла;
- `sellersCount` == количеству элементов исходного `offers`, у всех есть ID, имя и положительная цена;
- `minPrice` исходного объекта == минимуму **всех** исходных предложений продавцов;
- цена каждой карточки в сокращённом реестре == реальному минимуму её исходного массива.

**Результат: 27/27 карточек успешно; 0 противоречий; 18/18 предварительных SKU имеют согласованные исходные предложения в снимке Алматы от 21.11.2026.** Это закрывает только проверку полноты *сохранённого массива* продавцов относительно счётчика Apify. Не доказывает полный рынок, актуальность, цену по всем городам, соответствие OEM, сторону установки, массу, наличие Omega.

Примеры исходной проверки: STINSS S2S1552: 2/2 продавца, минимально 12 784 ₸; STINSS S2S1372: 4/4, минимально 14 822 ₸; Superzing 365757: 16/16 продавцов, минимум 5 320 ₸, **исключён и не восстановлен**. Последний проверен как контрольный пример; он **не входит** в 27 карточек 18 кандидатов. Машинный журнал по 27: [`docs/data/kaspi_20261122_candidate_raw_offer_validation_run9.json`](data/kaspi_20261122_candidate_raw_offer_validation_run9.json).

## Выявлена и устранена узкая ошибка сопоставления на staging

Ранее `strict_apify_prepublication.py` проверял, что целевой артикул встречается в названии и URL-slug. Если объявление продаёт **57409**, но одновременно пишет «аналог **163827**» и повторяет оба артикула в URL, при проверке только target SKU **163827** карточка могла ошибочно считаться оригинальным 163827. Предыдущий регрессионный тест проверял ситуацию, когда в URL встречался только основной артикул, и поэтому уязвимость не покрывал.

Добавлен fail-closed отказ от автоматического сопоставления для объявлений с явными маркерами аналога/замены в названии или URL (только ручная идентификация). Добавлено три регрессионных теста (русские и латинские варианты, маркер `replacement` в URL). Эти изменения сделаны только в review-ветке (коммиты `2fbe7d0`, `f954955`, исправление границ регулярных выражений `8d671fd`).

**CI именно после этого изменения пока не подтверждён**: прошлые 30/30 успешных тестов относились к более раннему коммиту `054b2c9`; не выдавать их за тест нового кода. Полные тесты Django/CI и интеграция в фактический процесс публикации не завершены. Отдельный Django importer `procurement/apify_price_recheck.py` пока не использует все защиты staging; не применять его результаты как основание автоматической публикации.
