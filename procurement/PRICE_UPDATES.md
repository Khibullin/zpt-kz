# Supplier price updates

`/office/procurement/price-updates/` accepts one to three XLSX/CSV/TSV files for existing suppliers. Sales/admin roles only. Files are validated before staging any run. Phaeton's two-line Almaty headers and Omega's wholesale headers are supported; other files need the documented canonical columns. Prices and Kaspi matches embedded in supplier files are intentionally ignored.

Validated normalized rows live in PostgreSQL, with a persistent cursor and per-run counters. Batches commit 200 rows at a time under a supplier lock. Full-catalogue absence reconciliation runs only after all rows finish. Partial updates never reconcile absent items. Full uploads below half the existing catalogue are rejected to prevent accidental stock removal. Conflicting duplicates and missing purchase prices are quarantined: existing stock becomes unknown; no arbitrary cost is chosen. User-specific commissions, orders, PP1/PP2 physical stock, and public catalogue products are untouched.

Gunicorn's `on_starting` hook starts one `process_price_updates --watch` consumer on the existing instance. `on_exit` forwards termination and reaps it. Set `PRICE_UPDATE_WORKER_ENABLED=false` to disable this consumer; authenticated page advancement and the one-shot management command remain available. PostgreSQL locks protect overlapping consumers during deploys. The consumer resumes only existing user-staged runs; it does not download supplier files or initiate scheduled uploads.

For verified bound Kaspi cards the consumer reads paginated sellers for Almaty, checks every row and waits for an empty final page. Repeated pages, invalid responses, 403/429, incomplete data and network failures never produce a complete snapshot. A source failure blocks pending bound-card tasks until an explicit retry. New cards stay pending for identity review through existing match imports. This implementation does not claim autonomous discovery or confirmation of unknown cards. Queue JSON and on-page links support that work.

Supplier observation and Kaspi price dates are independent. Existing mixed `checked_on` dates are migrated as supplier dates; a Kaspi price date is restored only from a complete matching snapshot with the same minimum price. An upload never refreshes Kaspi facts. Matching shared offers requires equal supplier name/variant, exact brand/article, matching package size and directly sourced identity proof; original dates are retained, demand is never copied. Seller observations for an identical verified card are reused within the same day.

Validation: 182 procurement tests, migrations on an isolated SQLite database, system check, migration drift check. Two existing tests were corrected to reflect the baseline office login redirect and measured 26-query rendering budget (both failures reproduced before these changes). Real Phaeton file: 27,882 source rows, 27,863 unique identities, 21 conflicts/missing prices; parsing and validation approximately 3 seconds, no live import performed.
